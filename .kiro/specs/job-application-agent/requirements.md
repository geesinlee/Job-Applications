# Requirements Document

## Introduction

The Job Application Agent is an AI-powered, end-to-end system for managing the full lifecycle of strategic job applications. It extends the existing `job_applications_mcp_server.py` (a Python/FastMCP thin orchestrator) into a comprehensive agent that can operate both as an interactive conversational assistant and as a set of MCP tools callable by AI models such as Claude.

The agent serves a senior enterprise sales professional (Client Partner / Account Executive level) applying primarily to technology companies for Singapore public sector and APAC-focused roles. It orchestrates JD ingestion, profile management, match scoring, CV gap analysis, learning program generation, document generation, application tracking, and follow-up management — across multiple roles and companies simultaneously.

The system is anchored to the user's LinkedIn profile as the canonical ground truth for work history and credentials, enriched by existing CV documents in the per-company folder structure. It integrates with external MCP servers (`ai-assistant`, `contacts`, `sgdi`, `gebiz-awards`) already available in the workspace, and is deployed on a fleet of local macOS devices sharing a common filesystem.

> **Dependency Note:** An `Agents.md` file referenced in the parent directory (`/Users/gslee/Projects/`) governs implementation rules, CI/CD standards, and deployment conventions for all agents in this project ecosystem. That document MUST be reviewed before implementation begins and its constraints treated as binding requirements.

## Glossary

- **Agent**: The Job Application Agent system, comprising the MCP server, data store, and workflow logic.
- **Application**: A single instance of the user pursuing a specific Role at a specific Company.
- **Base_CV**: The canonical, un-tailored CV document. Currently the DXC Client Partner Markdown version, which is the richest representation of the user's career history.
- **Company**: A target employer entity (e.g., Gartner, Salesforce, DXC). One Company may have multiple open Applications.
- **Company_Folder**: The per-company directory on disk (e.g., `/Users/gslee/Projects/Job-Applications/Gartner/`) where all application artefacts for that company are stored.
- **Cover_Letter**: A tailored, company- and role-specific cover letter document generated by the Agent.
- **Gap_Analysis**: The structured output comparing the user's Profile against a JD, identifying missing skills, experience, or credentials.
- **JD**: Job Description — the structured text of a job posting, normalised from PDF, Markdown, or URL input.
- **JD_Ingestor**: The subsystem responsible for accepting JD input (file or URL), parsing it, and persisting a structured JD record.
- **Learning_Program**: A structured, time-boxed self-study plan generated to close identified skill gaps.
- **LinkedIn_Profile**: The user's LinkedIn profile page, treated as the authoritative source of record for work history, education, and credentials.
- **Match_Score**: A numeric score (0–100) and accompanying reasoning indicating how well the user's Profile matches a given JD.
- **MCP_Server**: The FastMCP Python server exposing Agent capabilities as MCP tools.
- **Profile**: The aggregated, AI-maintained representation of the user's work history, skills, education, and credentials — sourced from LinkedIn and enriched by session-collected information.
- **Profile_Store**: The persistent storage layer for the user's Profile (JSON or structured Markdown file, stored in the project root).
- **Role**: A specific job title and position within a Company (e.g., "Strategic Account Executive – Large Accounts" at Gartner).
- **Stage**: A named phase in the application lifecycle: `new`, `applied`, `screening`, `interview_r1`, `interview_r2`, `interview_r3`, `offer`, `accepted`, `rejected`, `withdrawn`.
- **Tailored_CV**: A version of the Base_CV rewritten to emphasise experience most relevant to a specific JD, without fabricating content.
- **Tracker**: The persistent application tracking data store (a structured JSON file at `{BASE_DIR}/tracker.json`).

## Requirements

### Requirement 1: JD Ingestion

**User Story:** As a job applicant, I want to ingest a job description from a file or URL, so that the Agent has a structured, queryable record of the role I am applying for.

#### Acceptance Criteria

1. WHEN a file path is provided and the file exists and has a `.pdf` extension, THE JD_Ingestor SHALL extract all readable text from the PDF and store it as a structured JD record.
2. WHEN a file path is provided and the file exists and has a `.md`, `.markdown`, or `.txt` extension, THE JD_Ingestor SHALL read the file content and store it as a structured JD record.
3. WHEN a URL is provided and the URL returns HTTP 200, THE JD_Ingestor SHALL fetch all visible text content from the page, extract the job description body, and store it as a structured JD record.
4. IF the provided file path does not exist, THEN THE JD_Ingestor SHALL return an error message identifying the missing path and SHALL NOT create a partial record.
5. IF a URL is provided and the URL is unreachable or returns a non-200 HTTP status, THEN THE JD_Ingestor SHALL return an error message identifying the URL and the failure reason, and SHALL NOT create a partial record.
6. WHEN a JD is ingested, THE JD_Ingestor SHALL extract and store the following structured fields where present: role title, company name, location, employment type, required skills, preferred skills, years of experience, and responsibilities summary. IF a field is absent from the source, THE JD_Ingestor SHALL store the field as null rather than omitting it from the record.
7. WHEN a JD is ingested and a Company and Role combination already exists in the Tracker, defined as an exact case-insensitive match on both company name and role title, THE JD_Ingestor SHALL update the structured fields and JD.md, and SHALL preserve the existing Stage and all previously saved artefacts.
8. WHEN a JD is successfully ingested, THE JD_Ingestor SHALL write the extracted plain-text JD content to `{BASE_DIR}/{Company}/JD.md` and SHALL return the structured fields to the caller.
9. IF a PDF file is provided and PyPDF2 extracts zero readable characters from all pages, THEN THE JD_Ingestor SHALL return an error message stating the PDF yielded no extractable text and SHALL NOT create a partial record.

### Requirement 2: Profile Management

**User Story:** As a job applicant, I want the Agent to maintain a comprehensive, persistent profile of my work history and skills, so that every match score, CV edit, and document generation is anchored to accurate, up-to-date professional information.

#### Acceptance Criteria

1. THE Profile_Store SHALL persist the user's Profile in a structured format that is readable and writable by the Agent across sessions, surviving process restarts.
2. WHEN the Agent is asked to refresh the Profile from LinkedIn, THE Agent SHALL accept a LinkedIn profile URL or exported profile text as input and SHALL extract work experience, education, certifications, skills, and headline into the Profile_Store only when a refresh is explicitly requested.
3. IF a LinkedIn profile URL or export text is provided and the Agent cannot recognise it as a valid LinkedIn profile format, THEN THE Agent SHALL return an error identifying the unrecognised input and SHALL NOT modify the existing Profile_Store.
4. WHEN new work experience or skill information is provided during a session, THE Agent SHALL merge the new information into the existing Profile_Store. IF a field being merged conflicts with an existing field, THE Agent SHALL retain both the existing and new values and add a conflict marker, unless the user explicitly requests an overwrite.
5. THE Profile_Store SHALL record a `last_updated` timestamp for each top-level section (work_experience, education, certifications, skills).
6. WHEN a Base_CV file is identified (the DXC Client Partner Markdown file is the initial default), THE Agent SHALL parse it and seed the Profile_Store with any fields not already present from the LinkedIn source.
7. IF the Profile_Store contains a field sourced from both LinkedIn and a CV and the values differ, THE Agent SHALL retain both values with a conflict marker identifying the source of each, rather than silently overwriting either value.
8. WHEN the user requests a profile summary, THE Agent SHALL return: current role, total years of experience calculated as the sum of non-overlapping employment durations rounded down to the nearest whole year, the top 5 skills ordered by frequency of appearance across all work experience descriptions, education credentials including institution name and degree title, and the `last_updated` timestamp for each top-level section.

### Requirement 3: Match Scoring

**User Story:** As a job applicant, I want the Agent to score how well my profile matches a job description, so that I can prioritise which roles to pursue and understand where I stand before applying.

#### Acceptance Criteria

1. WHEN a Match Score is requested for a given Application, THE Agent SHALL compare the structured JD fields against the user's Profile and SHALL produce a Match_Score between 0 and 100 inclusive, where 0 represents no match and 100 represents a complete match across all evaluated dimensions.
2. THE Agent SHALL compute sub-scores for the following five named dimensions, each between 0 and 100, and SHALL combine them into the overall Match_Score using these weights: required_skills_match (40%), years_of_experience_match (25%), seniority_alignment (15%), industry_domain_alignment (10%), preferred_skills_match (10%).
3. WHEN producing a Match_Score, THE Agent SHALL output a human-readable reasoning section of no more than 500 words explaining the score, identifying up to 3 strengths and up to 3 gaps, listing as many as are available when fewer than 3 exist.
4. WHEN a Match_Score is produced, THE Agent SHALL persist it in the Tracker record for the Application, tagged with the computation timestamp in ISO 8601 UTC format (e.g., `2026-08-02T14:30:00Z`).
5. IF the Profile has not been initialised (Profile_Store is empty or missing), THEN THE Agent SHALL return an error requesting the user to initialise the Profile before scoring.
6. IF the JD has not been ingested or has no structured fields, THEN THE Agent SHALL return an error identifying that JD ingestion must be completed before scoring.
7. WHEN a JD requires skills or experience not present in the Profile, THE Agent SHALL include those items explicitly in the Match_Score output under a `missing_skills` field, covering both required and preferred JD skills absent from the Profile, to enable Gap_Analysis.

### Requirement 4: CV Gap Analysis and Edit Recommendations

**User Story:** As a job applicant, I want the Agent to identify specific gaps between my CV and the job description, so that I know exactly what to add, reframe, or emphasise before submitting.

#### Acceptance Criteria

1. WHEN a Gap_Analysis is requested for an Application, THE Agent SHALL compare the JD's required and preferred criteria against the Base_CV content and SHALL produce a structured list of gap items, each containing: gap_id (unique identifier), category, jd_criterion, affected_cv_section, current_text_excerpt, and recommendation.
2. THE Agent SHALL classify each gap into one of three categories: `missing` (the skill or experience does not appear anywhere in the CV), `understated` (the skill or experience appears in the CV but not in the first two bullet points of the most relevant role section), or `mismatch` (the skill or experience appears in the CV but is framed for a different industry or context than the JD requires).
3. WHEN a gap has category `missing`, THE Agent SHALL set current_text_excerpt to null and SHALL provide recommended addition text as the recommendation.
4. WHEN a gap has category `understated` or `mismatch`, THE Agent SHALL populate current_text_excerpt with the verbatim text from the CV and SHALL provide a specific replacement or reordering instruction as the recommendation.
5. THE Agent SHALL NOT fabricate experience, credentials, or achievements. WHEN generating recommendations, THE Agent SHALL only suggest reframing, reordering, or expanding on content already present in the Base_CV or Profile_Store.
6. IF the Base_CV cannot be located or the Profile_Store is empty at the time of Gap_Analysis request, THEN THE Agent SHALL return an error identifying the missing source and SHALL NOT produce a partial gap list.
7. WHEN a Gap_Analysis is produced, THE Agent SHALL save the output to `{Company_Folder}/gap_analysis.md`.
8. WHEN the user accepts a set of edit recommendations, THE Agent SHALL apply those recommendations to generate the Tailored_CV per Requirement 6, treating the accepted recommendations as the diff instruction set.

### Requirement 5: Learning Program Generation

**User Story:** As a job applicant, I want the Agent to generate a structured learning plan for skill gaps identified in the gap analysis, so that I can build genuine capability for roles where I am not yet fully qualified.

#### Acceptance Criteria

1. WHEN a Learning_Program is requested for an Application and a Match_Score exists for that Application, THE Agent SHALL use the `missing_skills` list from the most recent Match_Score as input. IF no Match_Score exists for the Application, THE Agent SHALL return an error requesting that Match Scoring be run first.
2. WHEN generating a Learning_Program, THE Agent SHALL produce a structured plan where each entry contains: skill name, recommended learning resource (course title, certification name, or documentation URL), estimated time commitment between 1 and 200 hours inclusive, priority level (`high`, `medium`, or `low`), and completion target of either 30, 60, or 90 days. THE Agent SHALL assign the 30-day target to `high` priority skills, the 60-day target to `medium` priority skills, and the 90-day target to `low` priority skills.
3. THE Agent SHALL assign priority `high` to skills listed as required in the JD, priority `medium` to skills listed as preferred in the JD, and priority `low` to skills that appear in the JD text but are not explicitly labelled as required or preferred.
4. THE Agent SHALL include at least one free or publicly available learning resource for each skill, in addition to any paid certifications.
5. IF the `missing_skills` list is empty, THE Agent SHALL return a response stating no skill gaps were identified and SHALL NOT create a learning_program.md file.
6. WHEN a Learning_Program is produced, THE Agent SHALL save it to `{Company_Folder}/learning_program.md`.
7. WHERE the identified skill gap corresponds to a vendor-specific platform (e.g., Snowflake, Databricks, Salesforce), THE Agent SHALL include the vendor's official certification pathway as the primary recommended resource and SHALL still include at least one free resource as a secondary entry.

### Requirement 6: Tailored CV Generation

**User Story:** As a job applicant, I want the Agent to produce a tailored, submission-ready CV for each application, so that my CV leads with the most relevant experience for that specific role.

#### Acceptance Criteria

1. WHEN a Tailored_CV is requested, THE Agent SHALL use the Base_CV as the primary input and, if a Gap_Analysis exists for the Application, SHALL use the accepted Gap_Analysis edit recommendations as secondary input. IF no Gap_Analysis exists, THE Agent SHALL proceed with Base_CV only and SHALL note the absence of gap analysis in the output.
2. WHEN generating the Tailored_CV, THE Agent SHALL reorder bullet points within each role section so that achievements whose text contains keywords matching the JD's required skills appear before other bullet points.
3. WHEN generating the Tailored_CV, THE Agent SHALL prepend a tailored professional summary of no more than 120 words that includes the target company name, the role title from the JD, and the top 3 strengths from the most recent Match_Score for the Application.
4. WHEN the Tailored_CV exceeds two pages in estimated length (where one page equals approximately 500 words), THE Agent MAY condense roles with end dates before 2010 to a single line containing only job title, company name, and date range.
5. THE Agent SHALL NOT alter any text segment from the Base_CV that contains a number followed by a currency symbol, percentage sign, or the words "ARR", "quota", "deal", or "target". Such segments MUST be copied verbatim into the Tailored_CV.
6. IF the Base_CV cannot be located, THEN THE Agent SHALL return an error identifying the missing source file and SHALL NOT produce a partial Tailored_CV.
7. WHEN a Tailored_CV is generated, THE Agent SHALL save it to `{Company_Folder}/CV_tailored.md`.
8. WHEN a Tailored_CV is generated, THE Agent SHALL also produce a diff summary saved to `{Company_Folder}/cv_diff_summary.md` listing every change made relative to the Base_CV, using the format: `[section] [change_type]: [description]`, where valid `change_type` values are `reorder`, `condense`, `add`, `remove`, or `replace`.

### Requirement 7: Cover Letter Generation

**User Story:** As a job applicant, I want the Agent to generate a polished, tailored cover letter for each application, so that my written pitch is compelling and directly addresses the role's requirements.

#### Acceptance Criteria

1. WHEN a Cover_Letter is requested, THE Agent SHALL read the JD, the Tailored_CV (or Base_CV if no tailored version exists), and any available company research from `{Company_Folder}/research.md` as context.
2. THE Agent SHALL support three writing tones: `bold`, `conservative`, and `storyteller`, selectable by the user, with `storyteller` as the default. IF an invalid tone value is provided, THE Agent SHALL return an error listing the three valid tone values and SHALL NOT generate a cover letter.
3. THE Cover_Letter SHALL be structured with: an opening paragraph addressing the hiring team, a body of no more than three paragraphs covering differentiators that directly correspond to requirements or responsibilities stated in the JD, and a closing paragraph containing an explicit request for a meeting or interview.
4. THE Agent SHALL embed at least one specific, quantified achievement from the user's Profile in the cover letter body. IF the Profile_Store contains no quantified achievement (no numeric value associated with a work outcome), THE Agent SHALL include the most senior role title and company name as a fallback and SHALL NOT fabricate a number.
5. WHEN a Cover_Letter is saved and no prior Cover_Letter.md exists in the Company_Folder, THE Agent SHALL write it to `{Company_Folder}/Cover_Letter.md` with no backup created. WHEN a Cover_Letter is saved and a prior Cover_Letter.md already exists, THE Agent SHALL rename the existing file to `Cover_Letter_v{N}.md` where N is the count of existing versioned backups plus 1, before writing the new Cover_Letter.md.
6. IF no company research file exists at `{Company_Folder}/research.md`, THEN THE Agent SHALL generate the Cover_Letter using JD and CV context only, and SHALL append a warning to the tool response (not to the Cover_Letter.md file) noting that company research was not available.

### Requirement 8: Document Export

**User Story:** As a job applicant, I want to export the tailored CV and cover letter as PDF or DOCX files ready for submission, so that I can attach them directly to job applications without manual reformatting.

#### Acceptance Criteria

1. WHEN an export is requested, THE Agent SHALL accept a `document_type` parameter of either `tailored_cv` (mapped to `CV_tailored.md`) or `cover_letter` (mapped to `Cover_Letter.md`), and a `format` parameter of either `pdf` or `docx`.
2. IF the source Markdown file identified by `document_type` does not exist in the Company_Folder, THEN THE Agent SHALL return an error identifying the missing source file and SHALL NOT produce an output file.
3. WHEN exporting to PDF, THE Agent SHALL produce a PDF that preserves Markdown heading hierarchy (H1, H2, H3), bold text, bullet points, and hyperlinks from the source Markdown file.
4. WHEN exporting to DOCX, THE Agent SHALL produce a DOCX file with margins of 2.54 cm on all sides, body text in Calibri or Times New Roman at 10–11 pt, and heading styles that mirror the Markdown H1/H2/H3 hierarchy.
5. WHEN an export is produced, THE Agent SHALL save the output file to `{Company_Folder}/{document_type}_{company}_{date}.{format}` where `{date}` is the current date in `YYYY-MM-DD` format (e.g., `CV_Gartner_2026-06-18.pdf`).
6. IF a required export dependency is not available in the runtime environment, THEN THE Agent SHALL return an error identifying the missing dependency and the installation command needed to resolve it.

### Requirement 9: Application Tracking

**User Story:** As a job applicant, I want to track the full lifecycle of every application in a single place, so that I always know the current status of each role and never miss a follow-up.

#### Acceptance Criteria

1. THE Tracker SHALL persist all application records in a structured file at `{BASE_DIR}/tracker.json`, with one record per Application (unique by Company + Role_Title).
2. WHEN an Application is created via JD ingestion, THE Tracker SHALL initialise the record with: company, role_title, date_created, stage (`new`), jd_path, and an empty history array.
3. WHEN a Stage transition is requested, THE Tracker SHALL update the Application's stage field and SHALL append a history entry containing: previous_stage, new_stage, and timestamp in ISO 8601 UTC format (e.g., `2026-08-02T14:30:00Z`).
4. THE Tracker SHALL enforce the following valid Stage transitions: `new → applied`, `applied → screening`, `screening → interview_r1`, `interview_r1 → interview_r2`, `interview_r2 → interview_r3`, `interview_r3 → offer`, `offer → accepted`, `offer → rejected`, `offer → withdrawn`. From any stage that is not `accepted`, `rejected`, or `withdrawn` (the terminal stages), a transition to `rejected` or `withdrawn` SHALL also be valid.
5. IF a requested Stage transition is not in the allowed transition map, THEN THE Tracker SHALL return an error identifying the invalid transition and SHALL NOT update the record.
6. WHEN a user queries all applications, THE Tracker SHALL return a list of all records sorted by date_created descending, with each record showing: company, role_title, current stage, date_created, and the timestamp of the most recent history entry (or date_created if the history array is empty).
7. WHEN a user queries applications by Stage, THE Tracker SHALL return only records matching the requested Stage.
8. THE Tracker SHALL support multiple Applications at the same Company (e.g., two roles at Salesforce), with each Application uniquely identified by the combination of company and role_title.

### Requirement 10: Multi-Role and Multi-Company Support

**User Story:** As a job applicant applying to multiple roles simultaneously, I want the Agent to manage each application independently, so that documents, scores, and tracking for one role do not contaminate another.

#### Acceptance Criteria

1. WHEN two Applications share the same Company but have different Role_Titles, THE Agent SHALL create separate sub-folders within the Company_Folder, structured as `{BASE_DIR}/{Company}/{Role_Slug}/` where Role_Slug is a URL-safe, lowercase representation of the Role_Title.
2. WHEN a single-role Company_Folder already exists from the legacy format (e.g., `Gartner/JD.md` with no sub-folder), THE Agent SHALL treat that folder as the primary role for that company and SHALL NOT migrate existing files automatically.
3. WHEN generating any artefact (JD.md, CV_tailored.md, Cover_Letter.md, etc.), THE Agent SHALL resolve the output path to the role-specific sub-folder when multiple roles exist for a Company, and to the Company_Folder root when only one role exists.
4. THE Agent SHALL provide a tool to list all active Applications grouped by Company, showing role titles and current stages.
5. WHEN the user specifies only a Company name (without a Role_Title) and multiple Applications exist for that Company, THE Agent SHALL prompt for disambiguation before executing any role-specific action.

### Requirement 11: Follow-up Management

**User Story:** As a job applicant, I want the Agent to track and remind me of follow-up actions after submitting applications, so that I maintain professional momentum and do not let opportunities go cold.

#### Acceptance Criteria

1. WHEN an Application transitions to Stage `applied`, THE Tracker SHALL automatically create a follow-up record with: action type (`send_follow_up_email`), due date set to 7 calendar days after the transition timestamp in UTC, and status `pending`. IF a `send_follow_up_email` follow-up record with status `pending` already exists for this Application, THE Tracker SHALL NOT create a duplicate.
2. WHEN an Application transitions to Stage `interview_r1`, `interview_r2`, or `interview_r3`, THE Tracker SHALL create a follow-up record with: action type (`send_thank_you_note`), due date set to 1 calendar day after the transition timestamp in UTC, and status `pending`. IF a `send_thank_you_note` follow-up record with status `pending` already exists for this Application, THE Tracker SHALL NOT create a duplicate.
3. WHEN the Agent is queried for due follow-ups, THE Agent SHALL return all follow-up records whose due date is earlier than or equal to the current UTC date and whose status is `pending`, sorted by due date ascending.
4. WHEN the user submits a request to mark a follow-up complete, THE Tracker SHALL update the follow-up record's status to `completed` and SHALL record the completion timestamp in ISO 8601 UTC format.
5. WHEN a follow-up action is due, THE Agent SHALL include a suggested follow-up message template in the response, personalised with the company name, role title, and the user's name.
6. IF a follow-up record's due date is earlier than the current UTC date and its status is `pending`, THE Agent SHALL flag the follow-up as `overdue` when returned in query results, but SHALL NOT delete or escalate the record automatically.
7. WHEN an Application transitions to Stage `interview_r1` or higher, THE Tracker SHALL set the status of any existing `send_follow_up_email` follow-up record for that Application from `pending` to `cancelled`.

### Requirement 12: Conversational and MCP Dual Interface

**User Story:** As a user of both Claude Desktop (conversational AI) and Claude Code (agentic IDE), I want the Agent to be accessible both as a conversational chat assistant and as a set of discrete MCP tools, so that I can interact with it naturally in either context.

#### Acceptance Criteria

1. THE MCP_Server SHALL expose the following tools via the FastMCP protocol, using snake_case verb-noun naming: `create_application`, `get_application_status`, `ingest_jd`, `score_match`, `analyse_gaps`, `generate_learning_program`, `tailor_cv`, `save_tailored_cv`, `generate_cover_letter`, `save_cover_letter`, `export_document`, `update_stage`, `list_applications`, `get_due_followups`, `mark_followup_complete`.
2. WHEN the Agent is invoked conversationally, THE Agent SHALL return a response composed of natural language prose in complete sentences. THE Agent SHALL NOT expose raw dictionary or JSON output directly to the user in a conversational response.
3. WHEN the Agent is invoked via MCP tool call, THE Agent SHALL return a dict whose values are only Python types that are JSON-serialisable (str, int, float, bool, list, dict, None). THE Agent SHALL NOT return Path objects or datetime instances in any tool response.
4. THE MCP_Server SHALL be registered in `.mcp.json` at `{BASE_DIR}/.mcp.json` with the key `job-applications`, using the Python/FastMCP stdio pattern consistent with the existing configuration.
5. WHEN the MCP_Server starts and BASE_DIR does not exist or is not a directory, THE MCP_Server SHALL exit with a non-zero exit code and SHALL write an error message to stderr identifying the missing BASE_DIR before any tool calls are accepted.
6. THE MCP_Server SHALL be stateless between tool calls; all persistent state SHALL be read from and written to the Company_Folder files (`JD.md`, `research.md`, `CV_tailored.md`, `Cover_Letter.md`, `gap_analysis.md`, `learning_program.md`, `pitch.md`, `territory_map.md`) on each invocation.

### Requirement 13: LinkedIn Profile Ingestion (Round-Trip)

**User Story:** As a job applicant, I want the Agent to parse my LinkedIn profile and preserve all structured data without loss, so that my profile is always an accurate digital twin of my professional record.

#### Acceptance Criteria

1. WHEN a LinkedIn profile URL is provided, THE Agent SHALL fetch the page and extract: headline, current position, all work experience entries (title, company, start month+year, end month+year or "Present", description), all education entries (institution, degree, field), certifications (name, issuer), and skills list.
2. WHEN a LinkedIn profile export file (PDF or TXT format as exported from LinkedIn) is provided, THE Agent SHALL parse the file and extract the same structured fields as criterion 1.
3. THE Profile_Store SHALL preserve all extracted LinkedIn fields using the same field names, nesting, and values as the source, and SHALL NOT truncate or summarise any field without explicit user instruction.
4. THE Profile_Store entry produced by parsing a LinkedIn profile SHALL satisfy the following round-trip property: serialising the entry to JSON and deserialising it SHALL produce a record where every field's type, content, and nesting structure is identical to the original, with no fields added, removed, or reordered. This property must hold for all valid, non-empty LinkedIn inputs.
5. WHEN a LinkedIn profile is parsed, THE Agent SHALL report: the count of work experience roles extracted, the count of skills extracted, the count of certifications extracted, and the count of education entries extracted.
6. IF a LinkedIn profile URL is provided and the page returns a non-200 status, requires login, or is detected as a private or blocked profile, THEN THE Agent SHALL return an error describing the access failure and SHALL NOT modify the existing Profile_Store.
7. IF a LinkedIn export file is provided and the file is empty, unreadable, or does not contain recognisable LinkedIn export fields (headline, experience, education), THEN THE Agent SHALL return an error identifying the file as unrecognised and SHALL NOT modify the existing Profile_Store.
8. WHEN a LinkedIn profile is parsed and one or more optional fields (certifications, education, skills) are absent from the source, THE Agent SHALL store the present fields, set the absent fields to empty list or empty string as appropriate, and SHALL include the count of each field type (including zero counts) in the extraction report.

### Requirement 14: Company Research Integration

**User Story:** As a job applicant, I want the Agent to orchestrate deep company research and persist the findings, so that my cover letters, pitches, and interview preparation are grounded in current, accurate intelligence.

#### Acceptance Criteria

1. WHEN company research is requested for a Company, THE Agent SHALL produce a research document with substantive content (not empty headings) covering: company overview, financial performance, Singapore/APAC presence, management team, competitors, employee sentiment, and Singapore government procurement footprint.
2. WHEN generating company research, THE Agent SHALL invoke the `gebiz-awards` MCP server using the Company name as the search term and SHALL include any matching procurement records in the research output. IF zero records are returned, THE Agent SHALL include a "No procurement records found" note in the procurement footprint section rather than omitting the section.
3. WHEN generating company research, THE Agent SHALL invoke the `sgdi` MCP server and the `contacts` MCP server and SHALL include any contacts whose organisation field matches or partially matches the Company name, with each contact showing at minimum: name, role, and organisation.
4. WHEN a research document is saved to `{Company_Folder}/research.md`, THE Agent SHALL include a metadata line in the format `> Generated: YYYY-MM-DD | Focus: {focus}` as the first content line after the document heading.
5. IF a research document already exists at `{Company_Folder}/research.md` and the `Generated` date in its metadata line is within 14 calendar days of the current date, THEN THE Agent SHALL return the existing document without re-running the research pipeline, unless the request includes `force_refresh=true` or the user explicitly requests a refresh in natural language.
6. WHERE the JD states that the role is based in Singapore or involves Singapore public sector clients, or WHERE the user has confirmed this, THE Agent SHALL include a dedicated section on known government agency relationships and active tenders in the research document.

### Requirement 15: Deployment and Configuration

**User Story:** As a developer deploying the Agent across a fleet of macOS devices, I want the Agent configuration to be portable and self-contained, so that it can be set up on any device without manual per-device customisation.

#### Acceptance Criteria

1. THE Agent SHALL read BASE_DIR, profile.json path, and tracker.json path from environment variables when present. IF an environment variable is set but the resolved path does not exist or is not accessible, THE Agent SHALL fail initialisation with an error message identifying the invalid path. IF environment variables are absent, THE Agent SHALL fall back to paths resolved relative to `__file__`. IF both resolution methods fail, THE Agent SHALL fail initialisation with an error message identifying the missing configuration rather than continuing in an undefined state.
2. THE MCP_Server's `.mcp.json` registration SHALL NOT contain absolute paths for any `args` or `cwd` fields that reference files within the `Job-Applications/` project directory.
3. THE MCP_Server MUST NOT hardcode absolute paths to files outside the `Job-Applications/` project directory (such as linked MCP servers like `ai-assistant` or `sgdi`). Those paths SHALL be configurable via environment variables or a local `.env` file.
4. WHEN the Agent initialises on a device where `tracker.json` does not exist, THE Agent SHALL create `tracker.json` with the content `{}` rather than erroring.
