## Part 1: Domain Model

### 1.1 Core Entities

#### CareerEvidence
Atomic, reusable career fact with source provenance and verification status.

```python
class CareerEvidence:
    """Atomic career fact with provenance and verification."""
    
    # Identity
    evidence_id: str  # UUID
    
    # Content
    statement: str  # e.g., "Grew revenue from $10M to $15M (50% growth) in Singapore region"
    evidence_type: Literal[
        "work_experience",     # Job history
        "achievement",         # Measurable outcome
        "skill",              # Technical or domain skill
        "domain_knowledge",   # Industry/vertical expertise
        "customer_example",   # Named/anonymized customer work
        "leadership",         # Team or program leadership
        "technical_knowledge", # Deep technical competency
        "language",           # Spoken/written language
        "certification",      # Formal credential
        "other"
    ]
    
    # Provenance (WHERE the fact came from)
    source_type: Literal[
        "baseline_cv",         # Original CV document
        "linkedin",            # LinkedIn profile snapshot
        "user_supplied",       # Supplied by user in gap interview
        "imported_document",   # Parsed from uploaded document
        "inferred",            # Derived from context (DO NOT USE IN CV AS FACT)
        "generated"            # Generated by LLM (DO NOT USE IN CV AS FACT)
    ]
    source_reference: str      # e.g., "DXC CV p1 line 5", "LinkedIn profile",
                               # "Gartner gap interview", "Imported from Workato resume"
    source_document_id: Optional[str]  # UUID of original CV/LinkedIn/import
    source_date: str           # ISO8601 when source was captured/created
    
    # Lifecycle tracking
    first_captured_at: str     # ISO8601 when first added to evidence repo
    last_confirmed_at: str     # ISO8601 when user last re-confirmed (updated on re-use)
    
    # Context of origin (if user-supplied)
    application_origin: Optional[dict] = {
        "application_id": str,     # UUID of Application record
        "company": str,            # Company name
        "role_title": str,         # Role title
        "date_supplied": str,      # ISO8601 when user supplied this fact
    }
    
    # Verification status
    verification_status: Literal[
        "unverified",     # Not yet confirmed by user
        "user_confirmed", # User has explicitly confirmed
        "inferred",       # Derived from other facts (cannot use in CV)
        "conflicted",     # Conflicts with other evidence (needs resolution)
        "superseded"      # Replaced by newer evidence
    ]
    confidence: Literal["LEVEL_A", "LEVEL_B", "LEVEL_C", "LEVEL_D"]
    user_confirmed: bool       # Explicit confirmation flag
    
    # Relationships (evidence can reference other evidence)
    supersedes: List[str]      # evidence_ids this fact replaces
    superseded_by: List[str]   # evidence_ids that replace this
    related_to: List[str]      # evidence_ids of related facts
    
    # Tagging (for matching to job requirements and sorting)
    competencies: List[str]    # e.g., ["Enterprise Sales", "AI Leadership", "GTM"]
    technologies: List[str]    # e.g., ["Salesforce", "Databricks", "Kafka", "Python"]
    industries: List[str]      # e.g., ["Financial Services", "Public Sector", "SaaS"]
    geographies: List[str]     # e.g., ["Singapore", "Malaysia", "APAC"]
    
    # Quantified metrics (if applicable)
    metrics: Optional[dict] = {
        "revenue": {
            "amount": float,
            "currency": str,  # "SGD", "USD", etc.
            "period": str,    # "FY2023", "Q1-Q4 2023"
            "verified_source": str  # "company announcement", "contract", "self-reported"
        },
        "quota_attainment": {
            "percentage": float,
            "period": str,
            "verified": bool
        },
        "customer_count": {
            "count": int,
            "period": str,
            "verified": bool
        },
        "team_size": {
            "count": int,
            "period": str
        },
        "growth_percentage": {
            "value": float,
            "period": str
        },
        # ... extensible dict
    }
    
    # Additional context
    notes: str                 # Caveats, context, related info
    
    # Audit trail
    created_by: str           # "baseline_import", "user:geesin", "app:claude"
    created_at: str           # ISO8601
    last_modified_by: str     # Who last updated verification status
    last_modified_at: str     # ISO8601
```

**Confidence Levels (DO NOT PROMOTE D TO CV)**

| Level | Definition | Example | Can Be in CV? |
|-------|-----------|---------|---------------|
| **A** | Strong: Specific example + role + action + quantified outcome | "Grew revenue 40% ($5M→$7M) as Regional VP, Singapore, 2022" | YES ✅ |
| **B** | Substantive: Specific responsibility; limited measurable outcome | "Led enterprise customer onboarding program; managed 15+ implementations" | YES ✅ |
| **C** | General: User confirms experience but limited detail | "Familiar with data platform architecture and enterprise integration" | CAUTIOUS ⚠️ (qualify with "exposure to" / "experience with") |
| **D** | Inference: Derived from context, not verified | "Likely has cloud deployment experience (inferred from company tech stack)" | NO ❌ |

#### JobRequirement
A requirement extracted from a job description, with evidence matching.

```python
class JobRequirement:
    """A requirement from a job description, matched to evidence."""
    
    # Identity
    requirement_id: str        # UUID
    application_id: str        # UUID of parent Application
    
    # Content (from JD analysis)
    category: Literal["mandatory", "preferred"]
    type: Literal[
        "technical_skill",       # "Python", "Salesforce"
        "domain_experience",     # "Enterprise AI adoption", "Public sector"
        "years_of_experience",   # "5+ years in enterprise sales"
        "seniority",             # "VP-level or equivalent"
        "responsibility",        # "Lead team of 10+"
        "soft_skill",            # "Communication", "Leadership"
        "behavior",              # "Comfort with ambiguity"
        "other"
    ]
    statement: str             # e.g., "5+ years leading enterprise AI adoption initiatives"
    extracted_from: dict = {
        "jd_path": str,        # Path to ingested JD
        "section": str,        # "Requirements", "Responsibilities", etc.
        "line_number": int,
        "text_excerpt": str    # Original text from JD
    }
    
    # Evidence matching
    matched_evidence: List[dict] = [
        {
            "evidence_id": str,
            "match_strength": Literal["STRONG", "ADEQUATE", "PARTIAL", "NO_EVIDENCE", "CONTRADICTORY"],
            "evidence_statement": str,
            "confidence_level": Literal["LEVEL_A", "LEVEL_B", "LEVEL_C", "LEVEL_D"],
            "gap_description": Optional[str],  # Why not STRONG (if applicable)
            "user_notes": Optional[str]
        }
    ]
    
    # Gap interview
    gap_status: Literal[
        "covered",           # Matched evidence exists
        "partial",           # Some evidence but not strong enough
        "missing",           # No evidence at all
        "clarification_needed",  # Conflicting evidence or unclear
        "user_supplied"      # User has supplied answer
    ]
    
    gap_interview_question: Optional[str]  # Question asked if gap detected
    user_response: Optional[str]           # Answer supplied by user
    evidence_created_from_response: Optional[str]  # evidence_id of newly created evidence
    
    # Outcome
    coverage_score: float      # 0.0–1.0, auto-calculated from matched evidence confidence
    required_for_cv: bool      # True if critical to demonstrate; used in draft strategy
    
    created_at: str
```

class Application:
    """Job application with embedded requirement analysis and evidence matching."""

    jd_source_url: Optional[str]
    
    # --- New fields (added in migration) ---
    
    # Requirement analysis
    requirements_extracted_at: Optional[str]  # ISO8601 when JD was analyzed
    requirements: List[str]    # List of requirement_ids
    requirement_analysis_quality: Optional[str]  # "auto" (regex) or "llm_analyzed"
    
    # Gap interview
    gap_interview_phase: Literal["not_started", "in_progress", "completed", "skipped"]
    gap_interview_questions: List[str]  # requirement_ids with gaps
    gap_interview_answers: List[dict] = [
        {
            "requirement_id": str,
            "question": str,
            "user_response": str,

#### CVRecord
A specific version of a CV, with evidence traceability.

```python
class CVRecord:
    """A CV version (draft, approved, final) with evidence traceability."""
    
    # Identity
    cv_record_id: str          # UUID
    application_id: str        # Parent Application
    
    # Version tracking
    version: Literal[
        "baseline",  # Original CV before tailoring
        "draft_1",   # First draft
        "draft_2",   # Second draft, etc.
        "approved",  # Final approved version (may have minor tweaks)
        "final"      # Version actually used for application
    ]
    version_number: int        # 0=baseline, 1=draft_1, etc.
    status: Literal["draft", "pending_review", "approved", "final"]
    
    # Content
    content: str               # Full CV markdown (or HTML if desired)
    
    # Traceability (the key innovation)
    evidence_used: List[dict] = [
        {
            "evidence_id": str,
            "evidence_statement": str,
            "cv_section": str,  # "Professional Summary", "Experience", "Skills", etc.
            "adapted_text": str,  # How it was reworded/adapted for this CV
            "confidence_level": Literal["LEVEL_A", "LEVEL_B", "LEVEL_C"],  # (D never in CV)
            "justification": str  # Why this evidence was included
        }
    ]
    
    # Change tracking (if draft, vs. baseline)
    major_changes: List[str]   # e.g., ["Added public-sector experience", "Reordered roles by recency"]
    changed_sections: List[str]  # e.g., ["Professional Summary", "Experience"]
    
    # Omissions (what was intentionally left out)
    significant_omissions: List[dict] = [
        {
            "evidence_id": str,
            "evidence_statement": str,
            "reason": str  # "Not relevant to role", "Already covered", "Weak evidence"
        }
    ]
    
    # Timestamps
    created_at: str            # ISO8601
    approved_at: Optional[str] # ISO8601 when user approved (null if still draft)
    finalized_at: Optional[str]  # ISO8601 when marked final
    
    # Lifecycle
    predecessor_id: Optional[str]  # cv_record_id of previous version (if revision)
    successor_id: Optional[str]    # cv_record_id of next version (if superseded)
    
    # Metadata
    created_by: str            # "app:claude" or user
    last_modified_by: str
    last_modified_at: str
```

### 1.2 Entity Relationships

```
Profile (existing)
  ├─ Contains: work_experience[], education[], skills[], conflicts[]
  └─ Does NOT contain: CareerEvidence[] (separate table)

CareerEvidence (new)
  ├─ Independence: Not part of profile (separate repo)
  ├─ Links back to: Profile (via source_reference) or Application (via application_origin)
  └─ Used by: Requirements, CV generation

Application
  ├─ Contains: JobRequirement[] (new)
  ├─ References: CareerEvidence[] (via matched_evidence, evidence_selected)
  ├─ Contains: CVRecord[] (new)
  └─ Extended with: gap_interview_phase, cv_records, cv_approved_at, etc.

JobRequirement
  ├─ Parent: Application
  ├─ References: CareerEvidence[] (via matched_evidence)
  └─ Produces: gap_interview_question (if gap detected)

CVRecord
  ├─ Parent: Application
  ├─ References: CareerEvidence[] (via evidence_used)
  ├─ Has: predecessor/successor (version chain)
  └─ Status: draft → pending_review → approved → final

VerificationEvent (optional)
  └─ Log entry for: CareerEvidence changes, CVRecord approvals
```

### 2.2 Migration Strategy

**Principle:** Reversible, non-destructive, backward-compatible.

#### Phase 1: Add New Fields (Non-Breaking)
1. Add `schema_version: "2.0"` to tracker.json root
2. Add new fields to each application record with **defaults**:
   - `requirements_extracted_at: null`
   - `requirements: []`
   - `gap_interview_phase: "not_started"`
   - `cv_records: []`
   - `cv_approved_at: null`
   - `cv_final_id: null`
   - `evidence_selected: []`
   - `evidence_omitted: []`
   - `discovered_at: date_created` (backfill from existing)
   - `applied_at: null`
   - `significant_decisions: []`

3. Create new `evidence.json` file (initially empty repository)
4. Create new `cv_versions.json` file (initially empty)

**Backward compatibility:** Existing code continues to work; old tools ignore new fields; new tools handle null/empty gracefully.

#### Phase 2: Baseline Evidence Import (One-Time)
1. For each user, parse `profile.json` and `{Company}/CV_*.md` files
2. Create CareerEvidence records for each profile.work_experience entry
   - source_type: "baseline_cv" or "linkedin" (based on _source field)
   - source_reference: "Profile seeding from {source}"
   - confidence: "LEVEL_A" (baseline CV is trusted)
   - verification_status: "user_confirmed" (user chose their CV)
   - user_confirmed: true
3. Create CareerEvidence for profile.skills[] (confidence: LEVEL_C, source: baseline_cv)
4. Store in evidence.json
5. **Reversible:** If user opts out, delete evidence.json and revert tracker.json schema_version to 1.0

#### Phase 3: Backfill CV Records for Existing Applications
1. For each application with existing CV_tailored.md:
   - Create CVRecord with version="baseline" (the original DXC CV)
   - Create CVRecord with version="final" (existing CV_tailored.md)
   - status: "final" (mark as already completed)
   - evidence_used: [] (not retroactively analyzed; future drafts will link)
2. Set application.cv_final_id to the final CVRecord id
3. Store in cv_versions.json

#### Phase 4: Preserve Existing Workflow (For Non-Evidence Apps)
- Applications created before this release continue in old workflow
- New applications created AFTER enable full evidence workflow
- Togglable via `ENABLE_EVIDENCE_WORKFLOW` env var (defaults to true)
- Tests cover both old and new paths

### 2.3 Backward Compatibility Rules

| Scenario | Behavior |
|----------|----------|
| Old tool calls save_tailored_cv on new app | Works; CV saved, no evidence linking yet |
| Old tool queries tracker.json fields | Works; new fields are null/empty (ignored) |
| Old MCP clients access server | Works; 31 existing tools remain unchanged |
| New tool queries evidence.json before import | Gracefully handles empty repo (returns []) |
| User reverts to old schema | Supported: delete evidence.json, tracker.json schema_version → 1.0 |
| Mixed old/new applications | Supported; each app tracks its own workflow_version |

## Part 5: Critical Design Decisions

### Decision 1: Evidence as Separate Entity (Not in Profile)
**Choice:** Separate `evidence.json` file, not embedded in `profile.json`

**Rationale:**
- Profile is baseline snapshot (CV + LinkedIn); evidence is accumulation across applications
- Evidence grows indefinitely; profile size should remain bounded
- Evidence needs rich provenance metadata; profile is simpler
- Easier to version, query, and audit separately

**Alternative rejected:** Embed CareerEvidence[] in profile.json
- Pro: Single file, simpler querying
- Con: Profile would grow 10x; mixes baseline with enrichment; harder to separate concern

---

### Decision 2: Confidence Levels (A/B/C/D Cannot Advance)
**Choice:** Hard rule — LEVEL_D and "inferred" source_type never appear in CV

**Rationale:**
- Specification requirement: "inferred and generated information MUST NOT be presented as established fact without explicit confirmation"
- Prevents LLM hallucination from silently entering application materials
- Requires explicit user confirmation to promote from D to C or better

**Implementation:**
- save_tailored_cv validator checks all evidence_used items
- If any have confidence=LEVEL_D, returns error: "Cannot generate CV with inference-only evidence; require user confirmation"

---

### Decision 3: CV Versioning with Approval Gate
**Choice:** Draft → Pending Review → Approved → Final (not draft → final direct)

**Rationale:**
- Specification requires explicit review opportunity before final
- Prevents accidental CV generation during refinement
- Provides clear decision point for "which CV was actually sent?"

**Implementation:**
- New application stage: AWAITING_CV_REVIEW (added to VALID_STAGES)
- save_tailored_cv creates a draft, sets application stage to AWAITING_CV_REVIEW
- approve_cv tool (new) moves to READY_TO_APPLY after user review
- mark_submitted creates final record after approval

**Backward compatibility:**
- Optional override: `save_tailored_cv(..., skip_review=False)` for old workflow
- Default: skip_review=False (enforce new gate)
- On existing applications: gate is optional (legacy apps skip if not enabled)

---

### Decision 4: Gap Interview Structured Capture
**Choice:** Dedicated MCP tool (capture_gap_response) to record user answers

**Rationale:**
- Ensures answers are parsed consistently, not lost in conversation
- Enables evidence creation and deduplication
- Creates audit trail of what user supplied when

**Implementation:**
- Tool signature:
  ```
  capture_gap_response(
    application_id,
    requirement_id,
    user_response_text,
    evidence_type="user_supplied"  # May be refined based on response analysis
  ) → CareerEvidence
  ```
- Tool validates:
  - Question actually exists for this requirement
  - Response is not empty
  - No obvious contradictions with existing evidence (warning if detected)
- Creates CareerEvidence with:
  - source_type: "user_supplied"
  - application_origin: {application_id, company, role_title, date_supplied}
  - verification_status: "user_confirmed" (user just confirmed by supplying it)
  - confidence: auto-determined based on response detail (C or B usually)

---

### Decision 5: Duplicate Detection (Semantic + Deterministic)
**Choice:** Two-pass approach — deterministic match first, semantic second

**Rationale:**
- Deterministic: Catch exact duplicates immediately (cheap)
- Semantic: Catch "same fact, different wording" (more expensive, optional)

**Implementation:**
```python
def find_duplicates(new_evidence):
    # Pass 1: Deterministic (normalize + hash)
    exact_matches = [e for e in all_evidence 
                    if normalized_statement(e) == normalized_statement(new_evidence)]
    
    # Pass 2: Semantic (optional, LLM-based)
    if exact_matches:
        return exact_matches  # Early exit
    
    semantic_candidates = semantic_search(new_evidence.statement, all_evidence)
    return [(e, similarity_score) for e in semantic_candidates if similarity_score > 0.85]

def normalized_statement(e):
    # Strip extra whitespace, lowercase, remove trailing punctuation
    return re.sub(r'[^\w\s]', '', e.statement.lower()).strip()
```

---

### Decision 6: Supersede vs. Overwrite
**Choice:** Never delete or overwrite evidence; use supersede relationships

**Rationale:**
- Audit trail: can recover why old fact was abandoned
- Contradiction detection: can compare old vs. new
- User can reconsider: reversible if they change mind

**Implementation:**
```python
def supersede(old_evidence_id, new_evidence_id):
    old = get_evidence(old_evidence_id)
    new = get_evidence(new_evidence_id)
    
    old.verification_status = "superseded"
    old.superseded_by = [new_evidence_id]
    
    new.supersedes = [old_evidence_id]
    new.verification_status = "user_confirmed"
    
    save(old)
    save(new)
    
    # Audit entry
    log_verification_event("evidence_superseded", old_evidence_id, new_evidence_id)
```

## Part 7: Critical Rules (Non-Negotiable)

1. **Evidence D Cannot Reach CV:** `confidence=LEVEL_D` or `source_type in ["inferred", "generated"]` → save_tailored_cv rejects with clear error

2. **Metrics Are Sacred:** For `revenue`, `quota_attainment`, `customer_count`, `growth_percentage` — must have `verified_source` field populated; cannot be estimated or assumed

3. **Contradictions Block:** If new evidence contradicts existing evidence (same statement, different value), system does NOT auto-overwrite; requires user clarification via resolve_contradiction

4. **Audit Trail Non-Deletable:** No delete_evidence tool; only supersede or mark_deprecated; all changes logged to VerificationEvent

5. **Application Survives Abort:** Application created at ingest_jd; if user abandons halfway, record persists with partial state (no loss of work)

6. **User Approval Gate Enforced:** Application cannot move to READY_TO_APPLY without user explicit approval of final CV (enforced in state machine validation)

7. **Version Linearity:** CVRecord versions form a chain (predecessor → successor); no branching; no merging of drafts

### Core Scenarios (Must Pass)

   - Source: "user_supplied", application_origin populated, user_confirmed: true

4. **Evidence Reused in Future Application**
   - First application: user supplies "Worked on Databricks in public sector"
   - Second application (different company): query_evidence finds "Databricks" → surfaces same fact
   - Reuse without user re-explaining

5. **Generated Content NOT Evidence**
   - tailor_cv creates reworded CV content
   - Content saved to CVRecord.adapted_text
   - NOT stored as new CareerEvidence
   - Not available for future application reuse

6. **Unsupported Claim Rejected**
   - User supplies: "I increased revenue by 500%"
   - With no source or verified_source
   - System flags: "Metric requires verified_source; rejected until user provides context"
   - Not added to evidence repo

7. **Contradictions Detected**
   - Baseline CV: "VP Sales, Singapore, 2021–2023"
   - User later supplies: "I worked in Singapore and Malaysia, 2021–2023"
   - System detects contradiction in geography scope
   - Prompts user: "Baseline says Singapore only; you now say Singapore+Malaysia. Which is correct?"
   - No silent overwrite

8. **Duplicate Evidence Handled**
   - User supplies: "Enterprise sales experience in APAC"
   - Later says: "Spent 3 years doing enterprise sales across Singapore, Malaysia, Thailand"
   - System detects semantic similarity
   - Offers merge: "Combine into one 'APAC enterprise sales' fact?"

9. **Draft CV Created Before Final**
   - save_tailored_cv creates draft, sets app stage to AWAITING_CV_REVIEW
   - Application.cv_records[0].status = "draft"
   - approve_cv required to move to READY_TO_APPLY

10. **Human Review Gate Enforced**
    - Application in AWAITING_CV_REVIEW stage
    - Cannot call save_final_cv directly
    - Must call approve_cv first (after user review)
    - approve_cv returns: draft, major_changes, evidence_used, omissions for user review

11. **Application Survives Partial Completion**
    - User ingests Gartner JD
    - Application created at ingest_jd time
    - User abandons (leaves conversation)
    - Next day, queries get_application(Gartner, role)
    - Returns: app in "new" stage, JD loaded, but no requirements/evidence/cv yet
    - No data loss

12. **Final CV Version Recoverable**
    - Application marked APPLIED with CV finalized
    - mark_submitted creates CVRecord(version=final)
    - Later user asks: "What CV did I send to Gartner?"
    - Query returns: exact markdown used, evidence_used[], confidence levels

13. **Second Application Leverages Enrichment**
    - First app (Gartner): User supplied "Led public-sector AI adoption at customer X"
    - Evidence created: LEVEL_B, application_origin: {Gartner, SAE}
    - Second app (Salesforce): analyse_requirements identifies "public-sector AI experience" gap
    - query_evidence finds Gartner-supplied evidence
    - Gap marked ADEQUATE (evidence exists), no re-interview needed

14. **Evidence Not Fabricated**
    - Baseline CV: "Grew revenue 40%"
    - No mention of which period, which product
    - User applies for role requiring "Enterprise AI adoption"
    - Gap analysis asks: "Did you lead or directly contribute to AI adoption?"
    - User responds: "Not directly, just familiar"
    - Evidence created: LEVEL_C (general), statement: "Familiar with enterprise AI concepts"
    - Not LEVEL_A claim of "led AI adoption" (would be fabrication)

15. **Previous Application Evidence Not Indiscriminately Copied**
    - First app (Gartner SAE): Evidence "Java development experience (side project)"
    - Second app (Salesforce Sales): analyse_requirements does not suggest Java experience
    - Query filters by competency/technology tags; Java doesn't match sales role
    - Evidence remains in repo but not surfaced as relevant gap

16. **Evidence Provenance Traceable**
    - Evidence used in Gartner CV: "Grew revenue 40%"
    - source_type: "baseline_cv", source_reference: "DXC CV line 23"
    - User later asks: "Where did this come from?"
    - Tool returns: full provenance (doc, location, when captured, confidence)

17. **Metric Verification Enforced**
    - User supplies: "Grew revenue from $5M to $8M"
    - System prompts: "Verified source? (baseline_cv, company_announcement, contract, self-reported)"
    - User supplies: "Company announcement 2023"
    - Evidence created with metrics.revenue.verified_source = "company_announcement"
    - Can be used in CV with confidence

18. **Contradiction Resolution Preserves History**
    - Conflict detected: baseline CV says "Singapore only"; user says "APAC"
    - User resolves: "APAC is correct; CV was old"
    - System:
      - Creates new evidence: "APAC coverage"
      - Marks old evidence: superseded_by
      - Logs VerificationEvent
      - Old evidence still queryable (can see why change was made)
